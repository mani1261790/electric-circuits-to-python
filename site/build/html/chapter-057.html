第57章　multicoreとcache coherence

57.1 二つのcoreが同じlineを見る

二つのcoreが同じmemory addressを読むと、各private cacheに同じcache lineのコピーを持てる。片方が書き込んだ後も、もう片方が古いコピーを読み続ければ、CPUとしては一つのmemoryを共有している契約が壊れる。cache coherence（cache一貫性）は、主に「一つのaddressについて、書込みと各copyの順序をどう見せるか」を定める。

coherenceはprogram全体の順序を自動的には定めない。どのaddressをどの順序で読むかというconsistency（整合性）とは別の層である。第56章のTLBはvirtual addressをphysical addressへ変換した後、ここではphysical cache lineを対象にする。

57.2 MESIの最小模型

一つのlineについて、M（Modified、dirtyな唯一のcopy）、E（Exclusive、cleanな唯一のcopy）、S（Shared、複数のclean copy）、I（Invalid、使用不可）を記録する。二coreの代表模型では、core 0がreadするとI->E、core 1もreadすると両方がS、core 0がwriteすると他方へinvalidateを送りcore 0をMにする。

write-invalidateでは、書込み前に他coreの同じlineをIへする。書込み後、他coreのread missは所有者からdataを受け取るか、memoryへwrite-backされた値を読む。transition表にはprocessor request、snoop event、source_kindを一行ずつ保存し、表にない遷移を黙って成功させない。

57.3 false sharingとdirectory

別の変数でも同じlineに載れば、core 0がxを書き、core 1がyを書くだけでinvalidateが往復する。これがfalse sharingで、値を共有していなくてもlineを共有することで遅くなる。ping-pongでは同じwordを交互に書き、producer-consumerではflagとdataのvisibilityを別のconsistency問題として記録する。

snoopingは全cacheがbusを監視する方式で、少数coreに分かりやすい。core数が増えるとdirectoryがsharer集合を持ち、必要なcacheだけへinvalidateを送る。本章の二core模型は、directoryの通信量や実装遅延を一般化しない。

57.4 予定traceと故障診断

予定runnerはcycle, core, address, line, request, state_before, snoop, invalidated, response_value, state_after, status, source_kind, measuredをJSONLへ出す。代表値はline size 64 B、address 0x1000、初期I/Iで、read/read/write/readの順を手で追う。期待値はI/I -> E/I -> S/S -> M/I -> S/Sである。

固定runnerの解析・契約再生は完了しているが、hitやinvalidationを外部toolや実機で測定済みとは扱わない。RTLをVerilatorへ載せる場合の候補条件と、Yosys形式検証の不変条件を別artifactへ保存する。SPICEはcache protocolを検証する手段ではなく、必要なtransistor波形は別の物理模型として切り分ける。FPGA経路は任意であり、board、clock、cache geometry、bitstream hashを記録できる時だけ別結果とする。外部RTL/SPICE/FPGA経路はplannedのまま維持する。

次章では、coherenceが守るaddress単位の一貫性だけでは足りない場面を、atomic命令とmemory modelで定義する。

57.5 一つのcache lineを表にして導出する

line sizeを64 B、xのaddressを0x1000とする。0x1000 // 64 = 64なのでline番号は64であり、0x1004も同じlineに入る。一方、条件変更でy=0x1040へ離せばline番号65になる。値を共有しなくても同じlineならinvalidateを受けるfalse sharingと、同じ値を読むためのcoherenceを分けて説明できる。

代表traceを、二つのcoreが同じlineを読むところから手で埋める。core0のread missはmemoryから値を受けてE、次にcore1がread missすると両方がS、core0がwriteするとcore1へinvalidateを送りM/I、最後にcore1がreadするとcore0の値を介してS/Sになる。

steprequestcore0core1lineの値診断
0初期状態IImemory=7まだcacheにない
1c0 read 0x1000E(7)I7exclusive候補
2c1 read 0x1000S(7)S(7)7sharedへ降格
3c0 write 9M(9)I9c1をinvalidate
4c1 readS(9)S(9)9ownerまたはmemoryから供給

step 3でcore1がIにならないなら、snoopのaddress比較、invalidateの宛先、またはresponse待ちの順序を疑う。x=0x1000,y=0x1038の交互writeだけ遅いなら、値の競合ではなくfalse sharingである。x=0x1000,y=0x1040へ離すと遅延が消える、という条件変更をrunnerの別caseにする。

この表が示すのは「同じaddressの値をどのcacheが持てるか」という境界であり、writeの後に別coreがいつ観測するかという順序までは決めない。実験は未実行のplanned traceで、source_kindとmeasured:falseを維持する。次章でこの観測順序をatomic命令とmemory modelへ接続する。

状態表を自分で作る

本文を読み終える前に、次の五列を紙またはテキストへ写す。『層』『入力』『内部状態』『上位の契約』『破綻条件』である。層には物理量、数値模型、回路、命令、OS、処理系のどれかを入れ、同じ名前の量を別層で使うときは型と単位を併記する。

内部状態から上位の契約へ進むとき、隠した変数を一つ選ぶ。たとえば連続電圧を論理値へ写すなら、しきい値の近くの電圧と雑音を隠している。命令列を関数呼出しへ写すなら、レジスタやstack pointerを隠している。隠した変数が変化しても契約が保たれる範囲が、その抽象化の強さである。

次に、同じ表へ失敗時の値を書く。未定義電圧、負の容量、範囲外アドレス、stack underflow、権限違反などは、正常なゼロや空文字へ丸めない。失敗を早い層で止め、診断名と入力を保存しておくと、後で別の層の故障と取り違えにくい。

故障診断の手順

故障は、入力、計算、表現、境界、出所の五分類で調べる。まず入力が有限で単位付きかを見る。次に計算の符号、係数、添字、丸めを確認する。その後、出力の表現幅、アドレス、状態名、source kindを確認する。最後に、予測を測定と呼んでいないか、上流の失敗を隠していないかを確認する。

  • two_modified: 入力はboth cores M for one line。期待する診断はmultiple_modified_rejectedで、正常値として続行しない。
  • stale_read: 入力はread from I line without data response。期待する診断はstale_copy_rejectedで、正常値として続行しない。
  • unknown_event: 入力はtransition event absent from MESI table。期待する診断はillegal_transition_rejectedで、正常値として続行しない。
  • consistency_mix: 入力はinfer fence ordering from coherence only。期待する診断はclaim_boundary_rejectedで、正常値として続行しない。

失敗を再現するときは、一度に一条件だけを変える。二つ以上を同時に変えると、どの境界が効いたか分からなくなる。エラーメッセージだけでなく、入力hash、章・実験ID、上流artifactの状態も保存する。

  • 受け取る: 前章で定義した入力を受け取る
  • 渡す: 次章へ検証済みの状態を渡す

模型の境界を言葉にする

  • 二core・一line・固定64 B・単純write-invalidateの模型で、directory規模や実CPUの性能を一般化しない。
  • coherence成立はconsistency・compiler ordering・fenceを保証しない。
  • 実機・FPGA・RTL runnerは未実行である。

境界を知ることは、式を弱めることではない。式が成立する条件を明示すれば、次により詳しい模型や測定へ進む理由を説明できる。逆に、条件を隠したまま桁の多い数値を出すと、精度ではなく誤解だけが増える。

8　ひとつの値を最後まで追う

この章で最も小さい代表入力を一つ選び、上位の問いから下位の実装へ、また下位の結果から上位の契約へ往復する。値の名前が層ごとに変わるときは、同じ行に別名を並べ、同一視してよい条件を右側に書く。

最初の行には、入力の出所と固定版を書く。二行目には、本文で導入した式または状態遷移を一つだけ置く。三行目には、式を評価する前の中間状態を書く。四行目には、計算後の値と残差を書く。五行目には、上位の契約へ戻るための不変条件を書く。

単位を持つ量は、数値の横へSI単位または宣言した単位系を必ず付ける。bit列は幅と符号解釈を付け、アドレスは対象memory領域を付ける。状態名は初期状態と更新順を付ける。tokenやASTはsource spanを付ける。これらを省略した値は、数字が同じでも別のcaseである。

途中で予測と結果が異なったら、最後の行から修正しない。入力、仮定、更新、表現、実行環境の順に一つずつ戻り、最初に不一致になった行へ診断名を付ける。診断名を付けられない差は、未解決として後段へ渡さない。

9　逆向きに説明する

今度は出力から出発し、どの入力と規則が必要だったかを逆向きに書く。画面の文字、論理値、レジスタ値、電圧、エネルギーのように異なる表現を、途中のartifactなしで直接つないではいけない。各矢印のそばに、保証する契約と保証しない詳細を一つずつ書く。

逆向きの説明で最初に見つかる欠落は、たいてい三種類のどれかである。入力の単位または幅がない、モデルの適用条件がない、または実行と測定の境界がない。この章の本文へ戻り、欠落を埋める行を一つ追加する。

10　再現記録の最小形

再現記録には、章ID、実験ID、case、入力hash、toolまたはmodelの版、終了コード、出力artifact、source_kind、status、measuredを残す。時刻やhost名は再現性の補助情報であり、計算値や状態遷移の一部として扱わない。

この最小形を満たせないときは、実験が難しいのではなく、契約がまだ閉じていない。閉じていない契約は、成功結果を保存するより先に、未指定欄と診断欄を保存する。
