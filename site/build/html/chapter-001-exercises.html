第1章　演習

演習では、先に自分の記録を書いてからヒントを見る。実験コマンドは教材共通runnerの実行入口であり、固定Linux環境で入力由来の契約を再生できる。CPython固有の観測、外部domain tool、実機測定は別経路なので、固定runnerの結果と混同しない。各問は、答えを読んだかではなく、最後の「再挑戦」を自分で説明できるかで合格とする。

E1　ASTとバイトコードの境界

次の二つを比較する。

print(1 + 2)
a = 1
b = 2
print(a + b)
  1. ASTで、最初の例の加算と二つ目の例の加算の入力がどのノードになっているか書く。
  2. ASTにBinOp(Add)があることから、CPUのADDが必ず実行されると言えない理由を書く。
  3. disの観測は、ASTに対してどの段階の情報を追加するか説明する。
ヒント
  • ヒント1: ASTはソースの構造で、実行手順そのものではない。
  • ヒント2: 最初の加算の左右はConstant、二つ目はNameである。
  • ヒント3: disが表示するのはCPythonの評価ループ向けの命令であって、RV32I命令ではない。

E2　定数畳み込みを確認する

print(1 + 2)について、次の二つの主張を「観測」「推論」「未確認」に分類する。

  • A: ASTに1、2、Addが現れる。
  • B: 基準CPythonのバイトコードに、定数3を読む形が現れることがある。
  • C: どのCPUでも加算器を通らない。
  • D: a = 1; b = 2; print(a + b)では、名前を読み出してから加算する形が比較対象になる。

次に、定数例に一行のコメントを追加しても計算結果が同じになる理由を、コメントが実行値に影響しない範囲で説明する。最後に、aまたはbを関数呼び出しの結果に置き換えたとき、定数畳み込みを無条件にはできない理由を書く。

ヒント
  • ヒント1: 「この入力とこの版で表示された」は観測、「すべてのCPUで」は一般化である。
  • ヒント2: 名前の値は、実行前に確定しているとは限らない。
  • ヒント3: Pythonの意味を変えない変換だけが許される。

E3　出力経路を分類する

本文の短縮システムコール列を使い、次の出来事を「Python処理系」「OSカーネルとの境界」「端末側」に分類する。

  1. printが整数を文字列表現へ変換する。
  2. ファイル記述子1へ"3\n"を渡す。
  3. writeの戻り値が2になる。
  4. 端末エミュレータが0x33を字形へ対応づける。
  5. フォントの字形が画素へラスタライズされる。

分類した後、「write成功」と「画面に見えた」が同じ主張でないことを一文で説明する。

ヒント
  • ヒント1: システムコールは、プロセスからカーネルへ依頼する境界である。
  • ヒント2: バイト列を文字や画素へする処理は、その境界の後にも残る。

E4　CPUトレースを手で進める

次の命令列について、各行の後のx5、x6、x7、x8、x10とUARTイベントを表にする。

addi x5,  x0, 1
addi x6,  x0, 2
add  x7,  x5, x6
addi x8,  x0, 51
lui  x10, 0x10000
sw   x8,  0(x10)
addi x8,  x0, 10
sw   x8,  0(x10)

追加課題として、3行目をsub x7, x5, x6へ変更した場合のトレースを作り、どの期待結果が壊れるかを記録する。x0が常に0であること、luiが上位20ビットを設定することを前提にしてよい。

ヒント
  • ヒント1: 1と2を加えるのは3行目である。
  • ヒント2: ASCIIの'3'は16進数0x33、十進数51である。
  • ヒント3: swはCPUが文字を表示する命令ではなく、メモリマップドUARTへ値を書き込む命令である。

E5　故障診断：改行がない

次のトレースは、数字3は出るが、端末のプロンプトが同じ行に続いてしまう。

pc=0x00000014  sw x8,0(x10)  UART[DATA]=0x33
program exited normally
  1. 観測された事実を二つ書く。
  2. もっとも小さい修正を、CPU命令または上位の出力処理として提案する。
  3. 修正後に期待するUARTイベントを示す。
  4. 「CPUが画面を描いた」と誤って結論しない理由を書く。
ヒント
  • ヒント1: 0x33は数字3であり、改行の値ではない。
  • ヒント2: 改行はASCIIの0x0aである。
  • ヒント3: UARTイベント、端末の解釈、画面更新を別々に記録する。

E6　故障診断：変数例を定数化し過ぎる

ある簡略コンパイラが、次のプログラムを常にprint(3)へ置き換えてしまう。

a = read_number()
b = 2
print(a + b)

入力が1なら3が出るが、入力が10でも3が出る。次を答える。

  1. どの変換が誤っているか。
  2. print(1 + 2)の定数畳み込みと何が違うか。
  3. 変換を許すために必要な条件を一つ以上挙げる。
  4. AST、バイトコード、実行結果のどこを追加観測すれば診断できるか。
ヒント
  • ヒント1: read_number()の戻り値は、実行前に確定した定数ではない。
  • ヒント2: 見た目が似た+でも、入力が定数か名前・呼出し結果かで安全性が違う。
  • ヒント3: 期待値を複数の入力で比較する。

E7　自然法則・模型・規格・実装を分ける

次の文を四分類し、分類の根拠を一行ずつ書く。

  1. RV32IのADDは二つのレジスタ値の和を宛先へ書く。
  2. CPUトレースではADDを一つの状態更新として表す。
  3. 信号の電圧は電荷と電場の状態に関係する。
  4. 教材のrv32eduではUARTを0x10000000に割り当てる。
  5. write成功後も端末エミュレータの処理が残る。

四分類に当てはめにくい文があれば、複数の層を混ぜていないかを確認し、二つ以上の文に分解する。

ヒント
  • ヒント1: 自然法則は、特定の教材実装だけに有効な約束ではない。
  • ヒント2: 規格は結果や境界の契約、実装はその契約を満たす具体的な選択である。
  • ヒント3: 模型は、都合よく隠した変数と成立範囲を持つ。

E8　三つの「アドレス」を分ける

次の三つを、それぞれ何のアドレスか説明し、同じ数値に見えても同一視できない理由を書く。

  1. Pythonのwriteへ渡される文字列のポインタ。
  2. プロセスの仮想アドレス空間にあるページ番号。
  3. rv32eduでUARTのデータレジスタへ割り当てた0x10000000。

最後に、「1のポインタをそのまま3の物理的なUART端子へ接続できる」と主張する説明を一文で反証する。

ヒント
  • ヒント1: 1は処理系とOSが使うプロセス内の住所である。
  • ヒント2: 2はCPUとOSのアドレス変換を経て、物理ページへ対応する。
  • ヒント3: 3はrv32eduが選んだMMIOの契約であり、DRAMの番地でも端子の電圧でもない。

合格の記録

次の四項目を自分の記録へ残す。

  • const/runtime二例のASTとバイトコードの差を、版依存部分と意味上の差に分けて説明した。
  • write、UARTイベント、端末表示を別々に説明した。
  • CPUトレースを一行ずつ再現し、subまたは改行欠落の故障を診断した。
  • 自然法則、模型、規格、実装を混ぜずに少なくとも一例ずつ説明した。

一つでも説明できない項目があれば、本文の該当節へ戻り、同じ問ではなく solutions.txt の再挑戦問題を解く。
