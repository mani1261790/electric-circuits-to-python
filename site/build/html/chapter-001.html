第1章　一行のPythonが通る全層

1　端末に現れた「3」を追う

次の二つのプログラムを用意する。

# const.py
print(1 + 2)
# runtime.py
a = 1
b = 2
print(a + b)

どちらも画面には同じ 3 と改行が現れる。しかし、同じ結果だからといって、途中の仕事まで同じとは限らない。最初の問いはこれである。

端末で python hello.py を実行したとき、文字 3 は、どの表現を通って画面へ届くのか。1 + 2 はいつ計算され、a + b はいつ計算されるのか。

この章では、答えを一つの説明に押し込めない。まず観測できるものを並べ、次にそれぞれが何を表しているかを区別する。後の章で電荷、場、回路、半導体、論理回路を詳しく扱うが、ここではまだ導出しない。

以下の実験番号は、共通実行入口へ接続した名前である。book run は固定Linux環境で解析契約を再生し、同じ入力から同じ種類の成果物を生成する。CPythonの版固有出力や実機の測定は別のdomain adapterとして扱い、ここで生成したtoy traceをそれらの観測値へ昇格させない。

book run 1 1   # AST とバイトコードの観測
book run 1 2   # プロセスとシステムコールの観測
book run 1 3   # 小さなCPUトレースの観測

実行結果のアドレス、命令オフセット、初期化時のシステムコールは、OS、ビルド、最適化によって変わる。変わらない意味と、変わり得る詳細を分けて記録する。

2　五つの窓

一行のプログラムには、少なくとも次の窓がある。

窓例その窓で見えるもの見えないもの
ソースprint(1 + 2)人が書いた文字列実行順序、機械命令
構文木Call(func=Name("print"), args=[BinOp(...)])文の構造と名前CPUのレジスタ、電圧
バイトコードLOAD_CONST、CALL処理系が選んだ仮想命令実CPUの配線、カーネル内部
システムコールwrite、exitプロセスとOSの境界Pythonの式の意図、MOSFET
CPUトレースADD、SW、PC命令、レジスタ、メモリ要求命令の意味を決める自然法則

さらに下には、メモリセルやUARTの端子の電圧、電荷、電磁場がある。3 という文字はそれ自体が電圧ではない。ある層では数値、別の層ではバイト列、さらに別の層では時間ごとに変化する信号である。

ここで「上の表現が下の表現に変換される」とだけ覚えるのは不十分である。変換は常に一対一ではない。構文木の一部は定数にまとめられることがあり、OSは多数の内部処理を一つのシステムコールとして見せる。各窓は、下位の詳細を隠しながら、上位の利用者に一定の約束を提供している。

3　ソース文字列を構文木にする

最初に、Pythonのソースを文字として読む。print(1 + 2) は空白を少し変えても、通常は同じ構造を表す。

import ast

source = "print(1 + 2)"
tree = ast.parse(source, filename="const.py", mode="exec")
print(ast.dump(tree, indent=2))

AST（抽象構文木、Abstract Syntax Tree）は、文字の並びから空白や括弧の一部を取り除き、意味に関係する構造を残した木である。出力の細部はPythonの版で変わり得るが、次の関係は観察対象になる。

公開APIとノードの意味は出典S1を参照し、固定runnerの解析artifactには入力と契約検査を添える。CPython固有のAST実行結果は外部domain実行として別に扱う。

Module
└── Expr
    └── Call
        ├── func: Name("print")
        └── args
            └── BinOp
                ├── left: Constant(1)
                ├── op: Add
                └── right: Constant(2)

この木では、1、2、加算、print の呼び出しが別々に表されている。ASTがこの形だからといって、実行時に必ずCPUの加算命令が一回現れるとは限らない。ASTは「ソースの構造」を表すものであり、「最終的な実行手順」ではないからである。

3.1 変数を置いた場合

次のソースを同じように解析する。

source = "a = 1\nb = 2\nprint(a + b)"
tree = ast.parse(source, filename="runtime.py", mode="exec")
print(ast.dump(tree, indent=2))

木には三つの文が現れる。

Module
├── Assign(targets=[Name("a")], value=Constant(1))
├── Assign(targets=[Name("b")], value=Constant(2))
└── Expr
    └── Call
        ├── func: Name("print")
        └── args
            └── BinOp
                ├── left: Name("a")
                ├── op: Add
                └── right: Name("b")

最初の例と違い、加算の入力は定数そのものではなく名前 a と b である。名前を現在の値へ解決する仕事が必要になり、コンパイラが安全に加算を先に済ませられるとは限らない。値を後で変更する機能、関数呼び出し、例外などが関わると、実行時に加算を残す必要がある。

4　構文木からバイトコードへ

CPythonでは、ASTの後にコードオブジェクトとバイトコードが作られる。dis（disassembler、逆アセンブラ）で、コードオブジェクトが持つ命令列を人が読める形へ表示できる。

disの公開APIはS2、基準実装の確認箇所はS3に対応づける。ただし、ここで表示する命令列をPython言語全体の規格とは扱わない。

import dis

dis.dis(compile("print(1 + 2)\n", "const.py", "exec"))
print("---")
dis.dis(compile("a = 1\nb = 2\nprint(a + b)\n", "runtime.py", "exec"))

ここで重要なのは、二つの表示を同じものとして扱わないことである。バイトコードはCPUの命令ではない。CPythonの評価ループが読む、処理系内部の命令形式である。

4.1 定数畳み込みは「加算が消えた」という意味

多くのCPythonビルドでは、print(1 + 2) のバイトコードに、1 と 2 を取り出して加算する命令ではなく、値 3 を定数として読み出す形が現れる。これはコンパイラが、値が変わらない式を前もって計算したためである。この変換を定数畳み込み（constant folding）と呼ぶ。

概念的には次のように見える。

ソース:       print(1 + 2)
AST:          Call(print, Add(1, 2))
バイトコード: 定数3を積む → printを呼ぶ

実際の命令名、オフセット、呼び出し形式はCPythonの固定版とビルド条件で確認する。ここで確定させたいのは、1 + 2 がASTに存在していても、実行時の加算として残るとは限らないという因果関係である。

一方、次の例では、少なくともソース上は値を名前から取り出してから加算する必要がある。

ソース:       a = 1; b = 2; print(a + b)
AST:          Assign, Assign, Call(func=Name("print"), args=[Add(Name(a), Name(b))])
バイトコード: aを保存 → bを保存 → aを読む → bを読む → 加算 → printを呼ぶ

最適化がどこまで許されるかは、Pythonの意味を壊さない範囲で決まる。a と b の値が別の処理によって変わる可能性を無視して、常に 3 に置き換えてよいわけではない。この二例は、trace Aの中で必ず対にして扱う。

4.2 何を観測し、何を推測したか

ast.dump と dis.dis の出力を表に記録する際は、次のように分ける。

記録種類言えること
BinOp(Add) がASTにある観測ソースの構文上、加算が書かれている
定数 3 を読むバイトコードがある観測このビルドでは実行前に結果を定数化した
いつ最適化したか追加観測が必要compileのどの段階で変換したか
CPUのADDがない限定付きの推論観測した実行経路ではCPU加算が見えていない

最後の行から「CPUでは絶対に加算していない」と一般化してはいけない。インタプリタの内部、JIT、デバッグ計測、別の処理系を選べば、異なる形があり得る。

5　プロセスとシステムコールの境界

バイトコードを読む処理系も、単独で空中に存在するわけではない。OSはプログラムをプロセス（process）として管理し、CPU時間、仮想アドレス空間、ファイル記述子などを割り当てる。Pythonが画面へ出力するとき、処理系は通常、OSが提供する出力経路を利用する。

システムコール（system call）は、ユーザープロセスがカーネルへ処理を依頼するための境界である。Linuxで観察する場合は、後でrunnerが固定環境内のシステムコール追跡機能を呼び出し、たとえば次の種類の行を保存する。

追跡器の使い方はS4を参照する。追跡器の出力自体も観測データであり、OSの普遍的な実行順序ではない。

execve(..., ["python", "const.py"], ...) = 0
...
write(1, "3\n", 2) = 2
exit_group(0) = ?

これは説明用の短縮例であり、現在の環境でこの行がそのまま得られることを約束するものではない。起動前のローダ、共有ライブラリ、標準入出力の初期化、メモリ割り当てによって、openat、mmap、read、close などが多数加わる。OSや追跡器によって名前や引数の表示も異なる。

それでも、write(1, "3\n", 2) のような行は、層をつなぐ大切な観測である。

  1. Pythonのprintは、文字列化と改行を含む出力要求を作る。
  2. 処理系または標準ライブラリは、ファイル記述子1へバイト列を渡す。
  3. OSのカーネルは、その記述子が指す出力先へ2バイトを書こうとする。
  4. 端末側では、バイト列を文字の表示へ変換する別の処理が続く。

printが直接画面の画素を書いているわけではない。writeが成功したことも、利用者の目に見える画素がすでに点灯したことを意味しない。ここには、端末エミュレータ、フォント、画像合成、表示装置という別の層がある。

5.1 システムコールの行を読み違えない

システムコール追跡には、三つの注意がある。

  • 表示される行と、プログラムが書いた行は違う。 追跡器自身が補足情報を追加することがある。
  • 一つのwriteと一つの画面更新は違う。 バッファリング、端末エミュレータ、表示更新のタイミングが間に入る。
  • OSの契約と実装は違う。 POSIXに似たインターフェースを持つOSでも、内部のスケジューラ、キャッシュ、ドライバは同じとは限らない。

この章で覚えるのは、システムコール名の暗記ではなく、「処理系とOSの境界を、観測可能なイベントとして切り出せる」ということだ。

6　仮想記憶は住所を隠す

バイトコード、文字列、スタック、ヒープは、処理系が使うメモリ上に置かれる。しかしプログラムが使うアドレスは、DRAMチップの物理的な番地そのものではない。プロセスは仮想アドレス空間（virtual address space）を持ち、CPUとOSの機構が仮想アドレスを物理メモリへ対応づける。

この対応づけにより、次の性質が得られる。

  • あるプロセスのアドレス 0x... を、別のプロセスがそのまま読むとは限らない。
  • 実際の物理ページは、必要になったときに割り当てられる場合がある。
  • 読み取り専用、書き込み可能、実行可能という権限をページごとに設定できる。

「writeの引数にある文字列のポインタが、DRAMのどのセルか」をこの章だけで一意に特定することはできない。ページ表、TLB、キャッシュ、メモリコントローラを観測する別の実験が必要だからである。ここでは、プロセスの見える住所と、下位の物理状態を同一視しないことが到達点になる。

7　小さなCPUトレースを読む

ここまでの説明は、実際のCPU命令をまだ見ていない。そこで、算術結果をUARTへ一文字ずつ送る小さな命令列を考える。これはPython処理系全体の逆アセンブルではなく、CPUとメモリマップドI/Oの境界を観察するための小さな模型である。

rv32eduでは、UARTのデータレジスタを 0x10000000 に置く。以下は、数値1と2を加え、ASCIIの3（0x33）と改行（0x0a）をUARTへ書く処理の一例である。命令の意味はRV32Iの範囲に限定し、PUTCのような架空のCPU命令は使わない。

ここでは、rv32eduのUART機器契約がswの書込みデータの下位8ビットをDATAとして受け取ると仮定する。この契約はRV32Iの命令仕様ではなく、machine specificationで固定する実装上の約束である。命令の一般的な意味はS5で確認する。

addi x5,  x0, 1       # x5 = 1
addi x6,  x0, 2       # x6 = 2
add  x7,  x5, x6      # x7 = 3
addi x8,  x7, 48      # x8 = x7 + 48 = ASCII '3' (0x33)
lui  x10, 0x10000     # x10 = 0x10000000
sw   x8,  0(x10)      # UARTへ '3'
addi x8,  x0, 10      # x8 = 改行
sw   x8,  0(x10)      # UARTへ改行

これはMiniPyが生成する最終コードを示すものではない。Pythonのprintには、名前の解決、整数の表現、文字列化、バッファリングなどの仕事がある。この短い列は、それらを済ませた後の「加算と出力」をCPUの観測対象へ切り出したものだ。

トレースは、少なくともPC、命令、書き込み後のレジスタ、メモリまたはデバイスイベントを持つ。

trace=A-runtime  pc=0x00000000  addi x5,x0,1       x5=0x00000001
trace=A-runtime  pc=0x00000004  addi x6,x0,2       x6=0x00000002
trace=A-runtime  pc=0x00000008  add  x7,x5,x6       x7=0x00000003
trace=A-runtime  pc=0x0000000c  addi x8,x7,48      x8=0x00000033
trace=A-runtime  pc=0x00000010  lui  x10,0x10000    x10=0x10000000
trace=A-runtime  pc=0x00000014  sw   x8,0(x10)      UART[DATA]=0x33
trace=A-runtime  pc=0x00000018  addi x8,x0,10       x8=0x0000000a
trace=A-runtime  pc=0x0000001c  sw   x8,0(x10)      UART[DATA]=0x0a

このトレースから確実に言えることは、模型上、ADDの結果をaddi x8,x7,48が受け取り、その値から作ったストアがUARTのデータレジスタへ届いたことである。UART[DATA]=0x33 は文字の意味をCPUが理解したことを示さない。CPUが書いたのは8ビットの値であり、それを端末がASCIIとして解釈する約束が別にある。

7.1 命令トレースと電気現象の距離

add x7, x5, x6 は、レジスタの値を加算器へ入力し、結果を次の状態へ保存するというCPU模型上のイベントである。実際の回路では、クロック、フリップフロップ、組合せ論理、信号遅延、電源電圧、温度などが関係する。さらに下では、MOSFETの電流と電荷、半導体中のキャリア、電磁場が関係する。

したがって、次の三つの文は別々に正しい。

  • 規格として: RV32IのADDは、二つの32ビットレジスタ値の和を宛先レジスタへ書く。
  • 模型として: addを1行の命令トレースとして表し、レジスタの値を整数で更新する。
  • 実装として: CPU回路は複数の論理ゲートと記憶素子の信号を、定められた時間内に変化させる。

この章では、実装の一例を自然法則そのものとして述べない。次章以降で、自然法則、理想化模型、規格、実装の境界を明示的に調べる。

8　自然法則、模型、規格、実装

同じ「3が表示された」という事実を、四種類の文に分ける。

自然法則

電荷、電磁場、半導体中のキャリア、導体の電流、電圧信号などは、物理法則に従う。0と1は自然界に刻印された二種類の粒子ではなく、回路が連続量の範囲を二つの論理値へ対応づけた記号である。

理想化模型

CPUトレースでは、レジスタを整数として扱い、命令を瞬間的な状態更新として表した。これは計算しやすい模型であり、電圧の立上り時間やノイズを捨てている。仮想記憶の説明でも、アドレス変換をページ表の対応として要約し、実際のTLBミスやページフォルトの時間を省いた。

規格・契約

Pythonの言語仕様、CPythonのast API、RV32Iの命令仕様、OSのシステムコールABIは、利用者と実装が共有する約束である。規格は「どの結果が保証されるか」を決めるが、内部でどの回路やアルゴリズムを使うかまで一つに決めるとは限らない。

特定実装

CPython 3.14.7のバイトコード、あるLinuxのシステムコール列、教材のrv32eduのメモリマップは、特定の実装と版に依存する。別のPython処理系、OS、CPUを使えば、同じ契約を別の手順で満たせる。

10　この章の観測結果

二つのソースを比べた結果を、次のように短く記録できる。

trace A-const
  source: print(1 + 2)
  AST: Add(Constant(1), Constant(2)) が残る
  bytecode: このCPython版では定数3を読む形になり得る
  syscall: 出力バイト列 "3\n" をOSへ渡す境界がある
  CPU: もし出力用コードを追えば、文字コードをUARTへ書く命令がある

trace A-runtime
  source: a=1; b=2; print(a+b)
  AST: Name("a") と Name("b") の加算が残る
  bytecode: 名前を読み、加算し、printを呼ぶ形を比較対象にする
  syscall: 同じ出力バイト列でも、そこへ至る上位処理は同一とは限らない
  CPU: 加算結果を作るADDと、出力先へのstoreを小さな例で観測する

print(1 + 2) と a + b が同じ結果を出したことは、二つのプログラムが同じ機械命令列であることを意味しない。逆に、同じバイトコード列になったとしても、CPUが同じ電気波形を通るとは限らない。境界ごとに、どの契約を検証したのかを明記する。

11　次に電荷と場へ戻る

この章で見た0、1、レジスタ、UARTバイトは、計算を説明するための上位の記号である。それらが実際の回路で使えるためには、信号がある電圧範囲に入り、ノイズや遅延の中でも受け手が同じ論理値として判断できなければならない。

さらに、電圧は一点だけに貼られた不変の札ではない。電荷の分布と電場、エネルギー、導体や絶縁体の性質を通して、回路の状態を要約する量である。次章からは、こうした「何を隠し、何を保証し、どこで破綻するか」を台帳へ記録しながら、0と1より下の物理量を学ぶ。

この章で、電荷や電場の式をまだ導出していないのは意図的である。printの一行から物理量までを一つの比喩で済ませず、観測した実装、採用した模型、共有された規格、成立している自然法則を別の問いとして扱うためである。

この章の模型は、適用範囲を明示して初めて安全に使える。次の限界を一つずつ、本文のどの主張に効くかと一緒に読む。
