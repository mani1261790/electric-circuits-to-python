第1章　解答と再挑戦

解答は、観測と推論を分けている。実際のrunnerが出す版依存の行は、ここに示す概念的な形と一致するかを確認し、オフセットやシステムコールの数だけで不正解にしない。

E1　ASTとバイトコードの境界

  1. print(1 + 2)では、Callの引数にあるBinOpの左右がConstant(1)とConstant(2)である。変数例では、a = 1とb = 2の代入の値は定数だが、最後のBinOpの左右はName("a")とName("b")である。
  2. ASTはソースの構造を表す。コンパイラは、意味を保てる範囲で構文を別の命令列へ変換できる。したがって、ASTのAddがCPythonのバイトコードの加算命令、さらに実CPUのADDへ一対一に対応するとは限らない。
  3. disは、ASTより後のコードオブジェクトが持つCPython向けバイトコードを表示する。これは「処理系が選んだ評価手順」を追加するが、OSのシステムコールや実CPU命令までは表示しない。

E2　定数畳み込みを確認する

  • Aは観測である。ASTを表示すれば、少なくとも対象版でその構造を確認できる。
  • Bは、対象の版とビルドに限定した観測または観測予定である。「常にそうなる」と一般化してはいけない。
  • Cは未確認かつ過大な推論である。CPython以外の処理系、JIT、処理系自身の内部実装まで調べずに、どのCPUでもと結論できない。
  • Dは比較対象としての観測・説明である。Nameの値を読み、必要なら加算する手順が残るかをdisで確認する。

コメントは字句解析の後に意味を持たない注釈として捨てられるため、実行される式や値を変更しない限り結果は同じである。ただしコメントを読んで実行する特殊な仕組みがあれば、その実装では別の契約になる。

read_number()は実行時に値を返す。入力、環境、関数内部の状態などによって結果が変わるため、コンパイル時にa + 2を3へ置き換えるとPythonの意味を壊す。定数畳み込みには、左右の値が実行時にも変わらず、演算に副作用や例外の差がなく、置換後も同じ観測結果になるという条件が必要である。

E3　出力経路を分類する

  1. Python処理系。整数を人が読む文字列へ変換し、改行を加える処理を含む。
  2. OSカーネルとの境界。プロセスがファイル記述子1へバイト列を書き込む要求である。
  3. OSカーネルとの境界から返る観測。writeが2バイトを受理したことを示す。
  4. 端末側。バイト列を文字コードとして解釈し、字形を選ぶ。
  5. 端末側または表示系。字形を画素へ変換する。

write成功が示すのは、OSが指定された2バイトを出力経路へ受け取ったということまでである。バッファ、端末エミュレータ、合成器、表示装置の後段が処理を終え、利用者の目に見えたことまでは示さない。

E4　CPUトレースを手で進める

初期値を全レジスタ0、UARTデータレジスタを0x10000000とする。

PC命令x5x6x7x8x10UARTイベント
0x00addi x5,x0,110000なし
0x04addi x6,x0,212000なし
0x08add x7,x5,x612300なし
0x0caddi x8,x0,5112351 (0x33)0なし
0x10lui x10,0x10000123510x10000000なし
0x14sw x8,0(x10)123510x10000000UART[DATA]=0x33
0x18addi x8,x0,1012310 (0x0a)0x10000000なし
0x1csw x8,0(x10)123100x10000000UART[DATA]=0x0a

sub x7,x5,x6へ変更すると、x7=0xffffffff（32ビットの二の補数表現で-1）になる。addi x8,x7,48は下位8ビットの0x2f（/）を作るため、UART出力も3ではなく/になる。このデータ依存を確認すれば、表示だけを固定値にしてADD故障を隠す誤りを検出できる。

E5　故障診断：改行がない

  1. 観測事実は、UARTへ0x33が一度書かれたこと、プログラムが正常終了したことである。改行イベントは観測されていない。
  2. 最小修正は、x8=10を作って同じUARTデータレジスタへもう一度storeすること、または上位の出力処理が改行バイトを追加することだ。
  3. 期待イベントは、順にUART[DATA]=0x33、UART[DATA]=0x0aである。
  4. CPUのstoreが示すのはUARTへバイトが渡ったことだけで、端末がバイトを解釈して字形を描いたことは別の層で起きる。

E6　故障診断：変数例を定数化し過ぎる

  1. read_number()の結果を定数1とみなし、a + b全体をコンパイル時に3へ置き換えた変換が誤りである。
  2. print(1 + 2)は左右がソース上の定数で、評価時の副作用や外部入力を持たないため、意味を保つ条件で3へ畳み込める。read_number()は実行時入力を読むため、同じ置換ができない。
  3. 少なくとも、aの値が実行前に確定していること、関数呼出し・入力・例外・可変状態などの観測結果が変わらないことが必要である。Pythonの名前束縛と評価順序も保存しなければならない。
  4. ASTでCall(read_number)とName(a)の関係を確認し、バイトコードで呼出し・名前の読み出し・加算が残っているかを調べ、1と10など複数入力の実行結果を比較する。

E7　自然法則・模型・規格・実装を分ける

  1. 規格・契約。 RV32Iという共有仕様が、命令の状態遷移を定める。
  2. 理想化模型。 実行を一つの状態更新として表し、遅延や内部ゲートを省いている。
  3. 自然法則。 電荷・電場・物質の応答に関する物理的関係である。ただしこの短文だけでは、どの近似式を使うかは未指定である。
  4. 特定実装。 教材のrv32eduが選んだアドレス割当で、RV32I全体の普遍的性質ではない。
  5. 実装または境界の観測。 write後にも端末側の処理が残るという、具体的な経路の説明である。OSや端末の実装を特定しないなら、厳密な規格主張ではない。

E8　三つの「アドレス」を分ける

  1. Pythonのwriteへ渡される文字列のポインタは、プロセスの仮想アドレス空間における実行時オブジェクトの位置を指す。ポインタ値そのものは、別プロセスや別実行で同じ場所を意味するとは限らない。
  2. 仮想アドレス空間のページ番号は、CPUがプロセスから見える住所をページ単位で表したものだ。ページ表とTLBを通って、実際の物理ページへ対応づけられる。
  3. 0x10000000はrv32eduのアドレス空間に置いたUART MMIO領域の先頭である。これはmachine specificationが定めるdevice accessの契約で、DRAMの番地でもUART端子の電圧でもない。

1のポインタを3のUART端子へ直接接続できるという主張は、プロセスの仮想アドレス、CPUの統一アドレス空間におけるMMIO、device内部の信号を一つの層へ混ぜているため誤りである。処理系がOSへ書込みを依頼し、CPUがMMIO storeを実行し、UARTがデータを受け取るという境界ごとの契約が必要になる。

再挑戦問題

解答を見た後は、次の問いを記録なしで解く。

R1　定数と名前

次の三つについて、加算を安全に前計算できるものと、できないものを理由付きで分ける。

print(10 * 20)
x = 10
print(x * 20)
print(int("10") * 20)

合格基準: 「ASTに定数がある」だけでなく、値が実行時に変わる可能性、副作用、例外の差まで言及する。

R2　経路の穴

次の記録には、CPUのUART storeまではあるが、端末へ届いたことを示す記録がない。

ADD result=3
UART[DATA]=0x33

不足している観測を二つ挙げ、それぞれがどの層に属するか説明する。

合格基準: 「画面に出た」とだけ答えず、UART受信・端末解釈・画面更新の少なくとも二段を区別する。

R3　模型の境界

「ADD一命令は常に1ナノ秒で完了する」という文を、規格、模型、実装、自然法則のどれとして扱うべきか。必要なら複数の文へ分解する。

合格基準: ISAの意味と、回路のtiming保証、特定CPUの測定値を分離する。

R4　アドレスの境界

「Python文字列のポインタが0x10000000なら、文字列を書けばrv32eduのUARTへ届く」という説明を、三つの境界を使って訂正する。

合格基準: プロセスの仮想アドレス、rv32eduのMMIOアドレス、UART device eventを別々に説明し、間にあるOSまたはCPUの契約を一つ以上挙げる。
