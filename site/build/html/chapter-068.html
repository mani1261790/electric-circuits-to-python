第68章　network interfaceからsocketまで

68.1 processのbyteはそのまま線へ出ない

Pythonのsocket.sendに渡したbyte列は、いくつものheaderとqueueを通る。socketはprocessが見るendpointの境界であり、NIC（Network Interface Controller）はhost memoryのbufferとlink側のframeをつなぐ。PHYはframeのbitを電気または光の信号へ変えるが、本章ではlink up/downと送信完了だけを抽象化する。

payload [72,105]を10.0.0.2:4000から10.0.0.3:9000へ送る例を用いる。送信元processが見ているのは2 byteで、UDP headerが8 byte加わる。さらにIP headerとEthernet headerが加わる。この「包む」操作をencapsulationと呼び、各層が付けたfieldを勝手に他層の値として解釈しない。

68.2 Ethernet frame

local linkではMAC addressを宛先と送信元に置いたEthernet frameを送る。toy入力の宛先は02:00:00:00:00:03、送信元は02:00:00:00:00:02、ethertypeはIPv4の0x0800とする。FCSは本章ではplaceholderにし、CRCの実装とlink測定を未実行のまま混ぜない。

NICのTX queueが満杯なら、socket.sendを成功扱いにするか、backpressureを返すかを決める。容量2へ3 frameを入れる代表例では、最初の2件を保持し、3件目を待たせる。frameがqueueへ入ったことと、相手がbyteを受け取ったことは異なるstatusである。

68.3 IP、UDP、ARP

IP packetはnetwork addressを、UDP datagramはportとlengthを持つ。UDPでは本章の固定subsetで、length=header 8+payload 2=10 byteとなる。受信側はMAC、IP、UDP portを順に確認し、該当socketへpayloadを渡す。portが未登録なら、frameを受け取ってもprocess byteにはならない。

IPからMACを知るtoy ARP cacheが空なら、まず10.0.0.3へのARP queryを出し、返答02:00:00:00:00:03を10 tick保持する。cache hitで送信する場合も、期限切れとquery失敗を別statusにする。ARPの実network全体のsecurityや競合解決をこの模型から主張しない。

68.4 receive path

受信は送信の逆順である。PHY/NICがframeを受け、MAC filter、IP header、UDP length、宛先portを検査し、payloadをRX queueへ置いてinterruptまたはpollingでprocessへ渡す。各段階にframe_id、layer、status、payload lengthを残す。linkで失われたframeと、受信後にheaderが壊れて拒否されたframeは異なる。

payload [72,105]が最終processへ届いたときだけ、socket receiveのbyte列として記録する。送信側のsentは相手側のreceivedの証拠ではない。toy simulatorでは、loss pointをlinkに固定したcaseを別に置き、decode errorと診断が分かれることを確認する。

68.5 層を越えて主張しない

予定実験はPythonのbyte/frame/packet/NIC queue模型を中心にし、Verilatorでqueueとcompletionの候補RTL、Yosysでlength・filter・順序の不変条件を確認する。ngspiceはPHYのRC edgeを考える任意模型に留める。実ケーブル、pcap、外部network、security、TCPの保証はこの草稿に含めない。

次章では、networkから得たsource textではなく、assembly sourceをmachine instructionへ変換する。どちらも「上位のbyte列を下位の形式へ包む」ように見えるが、assemblerはaddressとlabelを解決する別の契約を持つ。

68.6 H i を一つのframeとして受信する

送信側endpointを10.0.0.2:4000、受信側を10.0.0.3:9000、payloadを[72,105]とする。UDP headerは8 Bなのでlengthは8+2=10 Bである。Ethernet frameでは宛先MAC 02:00:00:00:00:03、送信元MAC 02:00:00:00:00:02、ethertype 0x0800を先に置き、FCSはこの模型ではplaceholderとして扱う。

状態表を自分で作る

本文を読み終える前に、次の五列を紙またはテキストへ写す。『層』『入力』『内部状態』『上位の契約』『破綻条件』である。層には物理量、数値模型、回路、命令、OS、処理系のどれかを入れ、同じ名前の量を別層で使うときは型と単位を併記する。

内部状態から上位の契約へ進むとき、隠した変数を一つ選ぶ。たとえば連続電圧を論理値へ写すなら、しきい値の近くの電圧と雑音を隠している。命令列を関数呼出しへ写すなら、レジスタやstack pointerを隠している。隠した変数が変化しても契約が保たれる範囲が、その抽象化の強さである。

次に、同じ表へ失敗時の値を書く。未定義電圧、負の容量、範囲外アドレス、stack underflow、権限違反などは、正常なゼロや空文字へ丸めない。失敗を早い層で止め、診断名と入力を保存しておくと、後で別の層の故障と取り違えにくい。

故障診断の手順

故障は、入力、計算、表現、境界、出所の五分類で調べる。まず入力が有限で単位付きかを見る。次に計算の符号、係数、添字、丸めを確認する。その後、出力の表現幅、アドレス、状態名、source kindを確認する。最後に、予測を測定と呼んでいないか、上流の失敗を隠していないかを確認する。

  • bad_mac: 入力はframe destination MAC does not match interface or broadcast。期待する診断はframe_filteredで、正常値として続行しない。
  • bad_length: 入力はIP declared header length smaller than minimum or inconsistent with bytes。期待する診断はheader_length_rejectedで、正常値として続行しない。
  • mtu_exceeded: 入力はpayload plus headers exceed MTU without fragmentation policy。期待する診断はmtu_rejectedで、正常値として続行しない。
  • unknown_port: 入力はaccepted packet has no bound socket。期待する診断はport_unreachable_diagnosticで、正常値として続行しない。
  • queue_overflow: 入力はthird frame into capacity-two TX queue。期待する診断はbackpressure_or_overflow_reportedで、正常値として続行しない。

前後の章へ渡すもの

この章は独立した計算帳ではない。前から受け取った量を、次の層が読める契約へ変換する。

  • 受け取る: 前章で定義した入力を受け取る
  • 渡す: 次章へ検証済みの状態を渡す

渡す値には、値だけでなく単位、版、source kind、status、measuredフラグを付ける。後章で同じ記号が現れたとき、初出の定義と再利用の条件を辿れるようにする。

模型の境界を言葉にする

  • 物理媒体はbit timingとlink up/downの抽象信号で扱い、PHY equalization・電磁波・実ケーブル特性を再現しない。
  • Ethernet/IP/UDP headerは教材用固定subsetであり、全option、IPv6、TCP輻輳制御を含まない。
  • socketはlocalhost toy endpointで、実networkの到達性・security・順序保証を主張しない。
  • packet lossとlatencyは指定したsimulator入力からの予定結果であり、実NICや回線の測定ではない。

境界を知ることは、式を弱めることではない。式が成立する条件を明示すれば、次により詳しい模型や測定へ進む理由を説明できる。逆に、条件を隠したまま桁の多い数値を出すと、精度ではなく誤解だけが増える。

最後に、代表実験を見ずに三つの文を書く。第一文は入力と単位、第二文は内部状態から出力までの一つの変化、第三文は最も近い破綻条件である。三文が書けたら、対応するartifactとrunnerの行を開き、本文の説明と同じtrace ID・statusになっているか照合する。

8　ひとつの値を最後まで追う

この章で最も小さい代表入力を一つ選び、上位の問いから下位の実装へ、また下位の結果から上位の契約へ往復する。値の名前が層ごとに変わるときは、同じ行に別名を並べ、同一視してよい条件を右側に書く。

最初の行には、入力の出所と固定版を書く。二行目には、本文で導入した式または状態遷移を一つだけ置く。三行目には、式を評価する前の中間状態を書く。四行目には、計算後の値と残差を書く。五行目には、上位の契約へ戻るための不変条件を書く。

単位を持つ量は、数値の横へSI単位または宣言した単位系を必ず付ける。bit列は幅と符号解釈を付け、アドレスは対象memory領域を付ける。状態名は初期状態と更新順を付ける。tokenやASTはsource spanを付ける。これらを省略した値は、数字が同じでも別のcaseである。

途中で予測と結果が異なったら、最後の行から修正しない。入力、仮定、更新、表現、実行環境の順に一つずつ戻り、最初に不一致になった行へ診断名を付ける。診断名を付けられない差は、未解決として後段へ渡さない。

9　逆向きに説明する

10　再現記録の最小形

再現記録には、章ID、実験ID、case、入力hash、toolまたはmodelの版、終了コード、出力artifact、source_kind、status、measuredを残す。時刻やhost名は再現性の補助情報であり、計算値や状態遷移の一部として扱わない。
