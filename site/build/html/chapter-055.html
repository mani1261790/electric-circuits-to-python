第55章　cacheと局所性

55.1 小さいmemoryが効く理由

CPUが大きなmemoryのすべてを毎回同じ時間で読む必要はない。近い時刻に同じ場所を再び読むtemporal locality（時間的局所性）と、読んだ場所の近くを続けて読むspatial locality（空間的局所性）があるからである。cacheは、memoryの一部を小さな高速lineとして保持し、次のaccessをhitまたはmissへ分類する。

cache lineは連続byteの単位で、setはlineを置ける場所、tagは同じset内でどのmemory blockかを識別する情報である。direct-mapped cacheなら、一つのblockは一つのsetにしか置けない。capacity、line size、set数、置換方式、write policyを固定しないhit率は比較にならない。

55.2 具体的なcacheを手で追う

代表モデルはcapacity 64 B、line size 16 B、4 setのdirect-mapped cacheとする。32-bit addressを、offset 4 bit、index 2 bit、残りをtagと分ける。block addressをaddress // 16、setをblock % 4として、各accessでtagを比較する。

比較のため、一つのsetに複数lineを置けるset-associative cacheも同じ容量で表す。例えば2 set×2-wayなら、同じsetへ二つのtagを保持でき、LRU（least recently used）などのreplacement policyで追い出すlineを決める。missの分類は、初めてlineを要求するcompulsory miss、cache全体の容量を増やせば減るcapacity miss、direct-mappedの置き場所競合をway追加で減らせるconflict missに分ける。本章の数値traceはdirect-mappedを必修の基準とし、set-associative比較は同じtraceを別geometryへ渡す予定caseである。

8×8のint32配列をrow-majorで走査すると、連続4要素が一つのlineへ入る。64 accessでは16回のcompulsory missと48 hit、hit率0.75という解析例になる。同じ配列をcolumn-majorで走査すると、行間のstrideが32 Bとなり、4 setの同じ場所を競合して、代表traceでは64 miss、hit率0となる。これはこのサイズと初期empty cacheに対する計算例で、別のcacheなら別の結果になる。

pointer chasingは、次のaddressが現在のload結果で決まるため、spatial localityを作りにくい。[0,64,128,192,256,320,384,448]を繰り返すtraceを別caseにし、順番が既知の配列走査と同じ「64 access」という数だけで比較しない。

55.3 AMATとwriteの境界

hit timeをT_hit、miss rateをm、miss penaltyをP_mとする単純な平均access timeはT_hit + m P_mである。penaltyに下位cache、主memory、queue待ちを含めるかを台帳に記録する。write-throughではstore hitをcacheと下位memoryへ同時に反映し、write-backではdirty bitを立ててevict時に一度だけ下位memoryへ書く。store missでlineを確保するwrite allocateと、cacheへlineを作らず下位memoryへ直接書くno-write-allocateも別方針である。本章の代表RTLはwrite-through・no-write-allocateを固定する。

55.4 予定実験

Python cache simulatorへrow-major、column-major、pointer-chasingの三つの具体的traceを渡し、access address、block、set、tag、hit/miss、line状態、hit率、AMATをJSONへ保存する。次の変更課題ではline sizeを8 Bへ変え、同じtraceでどの局所性が有利になるかを説明する。発展課題として小さなdata cacheをRTLへ加えるが、単一coreのin-order bus契約を越えるcoherenceは要求しない。

実験とRTLはplannedであり、hit率は代表入力からの解析予測で、測定結果ではない。SPICEはcache mappingの出所ではなく、必要ならSRAM cellの物理遅延を別章の別artifactとして扱う。FPGAでcacheが動いても、容量、初期化、write policy、clock条件を保存しない限り、本文の模型を検証したことにはならない。

55.5 故障診断と次章

hit率が合わないとき、まずaddressのbyte/word単位、line size、set数、初期状態、走査順を照合する。tag比較前にoffsetを捨てる、同じsetのevictionを記録しない、prefetchを無意識に入れる、AMATへmiss penaltyを二重加算する、が典型的な故障である。cacheが隠すのは速度差であって、process間の保護ではない。次章では、virtual addressをpage tableとTLBで変換し、保護とcacheを分けて考える。

状態表を自分で作る

本文を読み終える前に、次の五列を紙またはテキストへ写す。『層』『入力』『内部状態』『上位の契約』『破綻条件』である。層には物理量、数値模型、回路、命令、OS、処理系のどれかを入れ、同じ名前の量を別層で使うときは型と単位を併記する。

内部状態から上位の契約へ進むとき、隠した変数を一つ選ぶ。たとえば連続電圧を論理値へ写すなら、しきい値の近くの電圧と雑音を隠している。命令列を関数呼出しへ写すなら、レジスタやstack pointerを隠している。隠した変数が変化しても契約が保たれる範囲が、その抽象化の強さである。

次に、同じ表へ失敗時の値を書く。未定義電圧、負の容量、範囲外アドレス、stack underflow、権限違反などは、正常なゼロや空文字へ丸めない。失敗を早い層で止め、診断名と入力を保存しておくと、後で別の層の故障と取り違えにくい。

故障診断の手順

故障は、入力、計算、表現、境界、出所の五分類で調べる。まず入力が有限で単位付きかを見る。次に計算の符号、係数、添字、丸めを確認する。その後、出力の表現幅、アドレス、状態名、source kindを確認する。最後に、予測を測定と呼んでいないか、上流の失敗を隠していないかを確認する。

  • address_unit_mismatch: 入力はword_address_passed_to_byte_addressed_cache。期待する診断はaddress_unit_must_be_declaredで、正常値として続行しない。
  • invalid_geometry: 入力はline_size=0_or_sets=3。期待する診断はcache_geometry_rejectedで、正常値として続行しない。
  • tag_before_offset: 入力はcompare_full_address_before_discarding_offset。期待する診断はmapping_order_rejectedで、正常値として続行しない。
  • hidden_prefetch: 入力はtrace_contains_undeclared_prefetch。期待する診断はundeclared_access_rejectedで、正常値として続行しない。

前後の章へ渡すもの

この章は独立した計算帳ではない。前から受け取った量を、次の層が読める契約へ変換する。

  • 受け取る: 前章で定義した入力を受け取る
  • 渡す: 次章へ検証済みの状態を渡す

渡す値には、値だけでなく単位、版、source kind、status、measuredフラグを付ける。後章で同じ記号が現れたとき、初出の定義と再利用の条件を辿れるようにする。

模型の境界を言葉にする

  • hit率は指定した容量・line size・set数・初期状態・traceに対する解析予測であり、全programや別cacheへ一般化しない。
  • AMATのmiss penaltyは下位cache・memory・queue待ちを含むかを固定した教育模型で、実CPUの測定値ではない。
  • RTL data cacheは一core・in-order・一outstanding request・coherenceなしの模型であり、FPGA配置配線や実機性能を含まない。

境界を知ることは、式を弱めることではない。式が成立する条件を明示すれば、次により詳しい模型や測定へ進む理由を説明できる。逆に、条件を隠したまま桁の多い数値を出すと、精度ではなく誤解だけが増える。

章末の自己確認

最後に、代表実験を見ずに三つの文を書く。第一文は入力と単位、第二文は内部状態から出力までの一つの変化、第三文は最も近い破綻条件である。三文が書けたら、対応するartifactとrunnerの行を開き、本文の説明と同じtrace ID・statusになっているか照合する。

8　ひとつの値を最後まで追う

この章で最も小さい代表入力を一つ選び、上位の問いから下位の実装へ、また下位の結果から上位の契約へ往復する。値の名前が層ごとに変わるときは、同じ行に別名を並べ、同一視してよい条件を右側に書く。

最初の行には、入力の出所と固定版を書く。二行目には、本文で導入した式または状態遷移を一つだけ置く。三行目には、式を評価する前の中間状態を書く。四行目には、計算後の値と残差を書く。五行目には、上位の契約へ戻るための不変条件を書く。

単位を持つ量は、数値の横へSI単位または宣言した単位系を必ず付ける。bit列は幅と符号解釈を付け、アドレスは対象memory領域を付ける。状態名は初期状態と更新順を付ける。tokenやASTはsource spanを付ける。これらを省略した値は、数字が同じでも別のcaseである。

途中で予測と結果が異なったら、最後の行から修正しない。入力、仮定、更新、表現、実行環境の順に一つずつ戻り、最初に不一致になった行へ診断名を付ける。診断名を付けられない差は、未解決として後段へ渡さない。

9　逆向きに説明する

今度は出力から出発し、どの入力と規則が必要だったかを逆向きに書く。画面の文字、論理値、レジスタ値、電圧、エネルギーのように異なる表現を、途中のartifactなしで直接つないではいけない。各矢印のそばに、保証する契約と保証しない詳細を一つずつ書く。

逆向きの説明で最初に見つかる欠落は、たいてい三種類のどれかである。入力の単位または幅がない、モデルの適用条件がない、または実行と測定の境界がない。この章の本文へ戻り、欠落を埋める行を一つ追加する。

10　再現記録の最小形

再現記録には、章ID、実験ID、case、入力hash、toolまたはmodelの版、終了コード、出力artifact、source_kind、status、measuredを残す。時刻やhost名は再現性の補助情報であり、計算値や状態遷移の一部として扱わない。

この最小形を満たせないときは、実験が難しいのではなく、契約がまだ閉じていない。閉じていない契約は、成功結果を保存するより先に、未指定欄と診断欄を保存する。

11　次章の読者への引き継ぎ文

最後に、次章の読者がこの章を読み返さなくても前提を再構成できる引き継ぎ文を書く。第一文はこの章が固定した定義、第二文は代表入力と途中状態、第三文は守る不変条件、第四文は最も近い破綻条件、第五文は未実行または未照合の境界である。

引き継ぎ文の主語を『この値は』だけにしない。『この模型では』『この版のtoolでは』『このmemory領域では』『このsource spanでは』のように、値の所有者を明記する。所有者が変わるところが、章間のbridgeであり、独立レビューが最初に読む境界である。

引き継ぎ文を書いたら、manifestの bridge_in と bridge_out、handoffのopen question、required artifactを照合する。本文に書いた橋と台帳の橋が異なる場合は、どちらかを勝手に合わせず、差分を未解決として残す。
