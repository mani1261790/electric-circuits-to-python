第45章　RISC-V RV32Iのprogrammer's model

第44章では、memory中のbit列を命令として読むstored-program machineを作った。ここでは、教育用機械の個別の配線から一段離れ、RISC-V RV32I（RISC-Vという固有名の32-bit integer base ISA）がprogramから何を見せるのかを固定する。RISC-Vは「Version 5」という展開語ではなく、RISC思想とVを組み合わせたISAの名称である。大切なのは、命令を「どう実装するか」より先に、「どの状態を、どの規則で変えるか」を決めることである。

45.1 programmer's modelは観測可能な契約

programmer's modelとは、命令を使う側から見える抽象である。本章のRV32I domainでは、XLEN（register幅）を32、汎用registerを32本、PC（program counter）を命令addressとして持つ。register名はx0からx31で、x0の読出しは常に0、x0への書込みは捨てる。これは「x0のcellへ0を物理的に書く」という意味ではなく、read/write interfaceの契約である。

通常の4-byte命令を順に読むなら、次のPCはPC+4である。分岐やjumpが成立すると、命令ごとに定めたtargetへ変わる。RV32Iの命令alignmentは4-byteを基準とする。ここでは圧縮命令（C extension）を有効にしないため、2-byte命令を混ぜない。PC、register、memoryのどれも、単なるPythonの整数変数と同じ意味ではない。32 bitの範囲へ戻すwrapと、x0を固定する処理を参照模型に明記する。

この抽象からは、register fileのport数、ALUの段数、pipelineの有無、cacheの構造は決まらない。同じISAを単一cycleで実装しても、多段pipelineで実装しても、規定された命令の結果が同じならprogrammer's modelは保てる。逆に、内部が動いて見えても、x0やPCの更新規則が違えばRV32I実装とは呼べない。

45.2 命令wordをfieldへ分ける

32 bitの命令wordには、少なくともopcode、rd、rs1、rs2、funct3、funct7が現れる。R-typeは二つの入力registerと一つの出力registerを持つ。例えばADD x5,x6,x7ではrd=5、rs1=6、rs2=7、funct3=000、funct7=0000000、opcode=0110011である。代表wordは0x007302B3となる。同じregister fieldでもfunct7=0100000ならSUBで、代表wordは0x407302B3になる。

I-typeはrs1と12 bit immediateを使う。ADDI x5,x6,-4では、数学的な-4を12 bitの0xFFCで保持し、実行時には32 bitへ符号拡張する。代表word0xFFC30293を単に4092として足すのは誤りである。短いfieldのbit列と、XLENへ拡張した後の値を別の欄へ保存する。

S-typeはstoreのようにrdを持たず、12 bit immediateを二つのfieldへ分割する。B-typeもbranch offsetをimm[12|10:5|4:1|11]のように散らして配置する。U-typeは上位20 bitを作り、J-typeはjump offsetを分割する。この不自然に見える配置は、すべての形式でregister fieldの位置を揃え、decode回路を規則的にするためである。fieldを読む順番を決めるだけでは足りず、各bitの位置、符号、alignmentを固定しなければならない。

45.3 immediateと有限幅

immediateは命令内に埋め込まれた定数である。I/S/B/J形式では、短いbit列を符号付きoffsetとして扱う場面がある。例えば0xFFCは12 bitでは-4であり、RV32の32 bitでは0xFFFFFFFCに符号拡張される。ゼロ拡張すれば4092になってしまうので、bit[11]を符号bitとして使う規則をdecodeとexecuteの両方に保存する。

加算結果は32 bitへ写像する。例えば0xFFFFFFFF + 1のbit結果は0x00000000である。これは数学的な整数が0だという主張ではなく、32 bit registerへ格納された結果である。carryやoverflowを必要とする別の命令・実装では、結果とflagを別に記録する。RV32Iの通常のADDが、一般的なCPUのflag registerを自動的に更新すると仮定してはいけない。

45.4 memory accessはaddressとbyte orderを持つ

LW x5,8(x6)は、x6の値に8 byteを加えたbyte addressから4 byteを読み、32 bitのx5へ格納する。x6=0x00002000ならaddressは0x00002008である。ここでのアドレスはISAの算術を説明する抽象的なtoy memory domainであり、rv32eduの物理memory map（第48章で固定）をまだ適用していない。SW x5,8(x6)も同じaddress計算を行う。例としてx5=0xDEADBEEFをlittle-endian memoryへ置くと、低いaddressからEF BE AD DEとなる。host Pythonがどのbyte orderを採用しているかに任せず、ISAのmemory contractへ書く。

本章の代表domainはword accessだけで、MMIO、cache、TLB、page fault、unaligned accessの詳細を含めない。これらを後の章で足す場合も、同じLWという名前のまま暗黙に意味を変えず、アクセス幅、alignment、例外を新しい契約として追加する。

45.5 branchとjumpはPCを変える

BEQ x5,x6,+16は、二つのregisterが等しいとき、現在のPCから16 byte離れたtargetへ移る。PC=0x1000ならtargetは0x1010、等しくなければ次の0x1004である。branch offsetはsignedで、命令配置のalignmentを満たす必要がある。比較が真かどうかと、targetをどう作るかを別欄に保存すると、branchの不具合を「比較の誤り」と「PC計算の誤り」に分けられる。

JAL x1,+32は、次の命令address0x1004をx1へlinkとして保存し、0x1020へ移る。JALR x1,0(x5)はx5にimmediateを加えたtargetを作ったあと、targetのbit 0を0にする。x5=0x2001ならtargetは0x2000である。ただし本章はC拡張を無効にしたRV32Iなので、最終targetは4-byte境界にも必要である。例えばraw targetが0x2002ならbit 0をclearしても0x2002のままで、instruction-address-misaligned faultとする。bit 0 clearだけで全alignmentを保証したとは扱わない。

45.6 encode/decodeを往復する

参照runnerでは、命令を構造化した入力からwordへencodeし、wordからfieldへdecodeし、再度encodeする。往復で同じwordになっただけでは、命令が有効だとは限らない。例えば0x00000000を無条件にNOPや合法命令として表示せず、RV32I domainでのillegal instructionとして診断する。unknown opcode、field幅の超過、branch offsetのalignment違反、未指定のsignednessはfail closedにする。

runnerのJSONには、入力field、raw word、復元immediate、PC、target、source_kind、statusを保存する。Pythonの予定出力はrunner_outputであって、rv32edu上の実行traceやFPGA上の電圧測定ではない。実行を始めるまで、図とartifactのmeasuredはfalseのままにする。specのrevisionと節番号はsource gateで確定する。

45.7 次章へ

RV32Iは、32本のregister、PC、memory、一定の命令形式をprogramへ提供する。この規則があれば、bit列の列を人間が読めるassemblyへ戻し、関数呼出し、stack、配列走査を表現できる。次章では、命令を一つずつ実行する時系列の中で、ra、sp、引数register、callee-saved registerをどう扱うかへ進む。ISAの形式が分かっても、複数命令が共有する局所状態の責任分担はまだ決まっていない。

本文を読み終える前に、次の五列を紙またはテキストへ写す。『層』『入力』『内部状態』『上位の契約』『破綻条件』である。層には物理量、数値模型、回路、命令、OS、処理系のどれかを入れ、同じ名前の量を別層で使うときは型と単位を併記する。

内部状態から上位の契約へ進むとき、隠した変数を一つ選ぶ。たとえば連続電圧を論理値へ写すなら、しきい値の近くの電圧と雑音を隠している。命令列を関数呼出しへ写すなら、レジスタやstack pointerを隠している。隠した変数が変化しても契約が保たれる範囲が、その抽象化の強さである。

故障診断の手順

故障は、入力、計算、表現、境界、出所の五分類で調べる。まず入力が有限で単位付きかを見る。次に計算の符号、係数、添字、丸めを確認する。その後、出力の表現幅、アドレス、状態名、source kindを確認する。最後に、予測を測定と呼んでいないか、上流の失敗を隠していないかを確認する。

  • x0_mutation: 入力はx0へ非零を書き込む。期待する診断はx0_write_ignored_and_loggedで、正常値として続行しない。
  • wrong_format: 入力はopcodeに対して別形式のfieldを解釈する。期待する診断はinstruction_format_mismatchで、正常値として続行しない。
  • immediate_without_sign: 入力はADDIの0xFFCを4092として扱う。期待する診断はsigned_immediate_requiredで、正常値として続行しない。
  • misaligned_target: 入力はbranch/jump targetをalignmentなしで受理する。期待する診断はinstruction_alignment_violationで、正常値として続行しない。
  • jalr_bit0: 入力はJALR targetのbit0を保持する。期待する診断はjalr_bit0_clear_requiredで、正常値として続行しない。
  • load_store_byte_order: 入力はDEADBEEFのbyte順をhost endianへ任せる。期待する診断はlittle_endian_contract_missingで、正常値として続行しない。
  • unknown_word: 入力は0x00000000を有効なRV32I命令と表示する。期待する診断はillegal_instructionで、正常値として続行しない。
  • runner_as_measurement: 入力はPython decode結果をCPU実測結果と表示する。期待する診断はsource_kind_mismatchで、正常値として続行しない。

失敗を再現するときは、一度に一条件だけを変える。二つ以上を同時に変えると、どの境界が効いたか分からなくなる。エラーメッセージだけでなく、入力hash、章・実験ID、上流artifactの状態も保存する。

模型の境界を言葉にする

  • RV32Iの仕様表は命令の観測規則を定めるが、内部datapath・pipeline・cacheを定めない。
  • 代表wordのencode/decodeはPython予定runnerの解析であり、CPU実機の命令実行測定ではない。
  • memory accessはlittle-endianと整列条件を固定した教材domainであり、MMIO・cache・page faultを扱わない。
  • 本章の固定runnerは契約を再生済みだが、測定とFPGA bitstreamは未実行・未取得である。

境界を知ることは、式を弱めることではない。式が成立する条件を明示すれば、次により詳しい模型や測定へ進む理由を説明できる。逆に、条件を隠したまま桁の多い数値を出すと、精度ではなく誤解だけが増える。

5　模型の境界と章間の橋

この章の模型は、適用範囲を明示して初めて安全に使える。次の限界を一つずつ、本文のどの主張に効くかと一緒に読む。

  • RV32Iの仕様表は命令の観測規則を定めるが、内部datapath・pipeline・cacheを定めない。
  • 代表wordのencode/decodeはPython予定runnerの解析であり、CPU実機の命令実行測定ではない。
  • memory accessはlittle-endianと整列条件を固定した教材domainであり、MMIO・cache・page faultを扱わない。
  • 本章の固定runnerは契約を再生済みだが、測定とFPGA bitstreamは未実行・未取得である。

前章から受け取るもの:

  • 第44章のstored-program machine、PC、memory、命令列と、第33章のbit列・2の補数を受け取る。

次章へ渡すもの:

  • 第46章へ、RV32Iのregister・memory・branch・jump規則をassembly、stack、calling conventionへ渡す。

橋を渡すときは、値だけでなく定義、版、status、measured、未対応条件を残す。同じ記号が次章で再登場しても、契約が同じとは限らない。

この章で最も小さい代表入力を一つ選び、上位の問いから下位の実装へ、また下位の結果から上位の契約へ往復する。値の名前が層ごとに変わるときは、同じ行に別名を並べ、同一視してよい条件を右側に書く。

最初の行には、入力の出所と固定版を書く。二行目には、本文で導入した式または状態遷移を一つだけ置く。三行目には、式を評価する前の中間状態を書く。四行目には、計算後の値と残差を書く。五行目には、上位の契約へ戻るための不変条件を書く。

単位を持つ量は、数値の横へSI単位または宣言した単位系を必ず付ける。bit列は幅と符号解釈を付け、アドレスは対象memory領域を付ける。状態名は初期状態と更新順を付ける。tokenやASTはsource spanを付ける。これらを省略した値は、数字が同じでも別のcaseである。

途中で予測と結果が異なったら、最後の行から修正しない。入力、仮定、更新、表現、実行環境の順に一つずつ戻り、最初に不一致になった行へ診断名を付ける。診断名を付けられない差は、未解決として後段へ渡さない。

9　逆向きに説明する

今度は出力から出発し、どの入力と規則が必要だったかを逆向きに書く。画面の文字、論理値、レジスタ値、電圧、エネルギーのように異なる表現を、途中のartifactなしで直接つないではいけない。各矢印のそばに、保証する契約と保証しない詳細を一つずつ書く。

逆向きの説明で最初に見つかる欠落は、たいてい三種類のどれかである。入力の単位または幅がない、モデルの適用条件がない、または実行と測定の境界がない。この章の本文へ戻り、欠落を埋める行を一つ追加する。

10　再現記録の最小形

再現記録には、章ID、実験ID、case、入力hash、toolまたはmodelの版、終了コード、出力artifact、source_kind、status、measuredを残す。時刻やhost名は再現性の補助情報であり、計算値や状態遷移の一部として扱わない。

この最小形を満たせないときは、実験が難しいのではなく、契約がまだ閉じていない。閉じていない契約は、成功結果を保存するより先に、未指定欄と診断欄を保存する。

11　次章の読者への引き継ぎ文

最後に、次章の読者がこの章を読み返さなくても前提を再構成できる引き継ぎ文を書く。第一文はこの章が固定した定義、第二文は代表入力と途中状態、第三文は守る不変条件、第四文は最も近い破綻条件、第五文は未実行または未照合の境界である。

引き継ぎ文の主語を『この値は』だけにしない。『この模型では』『この版のtoolでは』『このmemory領域では』『このsource spanでは』のように、値の所有者を明記する。所有者が変わるところが、章間のbridgeであり、独立レビューが最初に読む境界である。

引き継ぎ文を書いたら、manifestの bridge_in と bridge_out、handoffのopen question、required artifactを照合する。本文に書いた橋と台帳の橋が異なる場合は、どちらかを勝手に合わせず、差分を未解決として残す。
